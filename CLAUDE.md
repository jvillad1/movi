## App

**Movi** — personal and family finance management app. Package: `com.jvillada.movi`. Design specs for
individual features live under `docs/superpowers/specs/` (one file per feature, dated); the original
core design is `2026-04-26-monedero-core-design.md`.

## Project structure

Movi follows the **2026-05 KMP default structure** (JetBrains): a pure KMP library is split from the per-platform application modules, so no multiplatform module applies `com.android.application` (required by AGP 9.0).

```
movi/
├── core/         Pure Kotlin multiplatform — models + repository + SQLDelight. Shared by server AND clients.
├── shared/       Compose Multiplatform UI library — Android (lib), iOS, Web (wasmJs). Produces the iOS XCFramework.
├── androidApp/   Android application (com.android.application) — MainActivity host. Depends on :shared + :core.
├── webApp/       wasmJs browser application — main() + index.html. Depends on :shared.
├── server/       Ktor JVM backend. Depends on :core.
└── iosApp/       Swift shell that embeds the ComposeApp XCFramework (built from :shared).
```

### Module dependency graph

```
shared      ──▶  core
androidApp  ──▶  shared, core
webApp      ──▶  shared
server      ──▶  core
iosApp      ──▶  shared   (ComposeApp XCFramework)
```

> **Naming note:** the Gradle module is `:core`, but its Kotlin package stayed `com.jvillada.movi.shared.*` (and the SQLDelight DB package is `com.jvillada.movi.shared.db`). The module was renamed `shared`→`core` at the Gradle/directory level only; packages were intentionally left untouched to avoid regenerating SQLDelight code and rewriting imports.

## Commands

### Backend & Web
```bash
# Run Ktor server (port 8080)
./gradlew :server:run

# Run web app in browser (Compose/Wasm)
./gradlew :webApp:wasmJsBrowserDevelopmentRun

# Build server fat JAR
./gradlew :server:buildFatJar

# Run tests — this is exactly what CI runs (.github/workflows/pruebas.yml), nothing more, nothing less
./gradlew --rerun-tasks :core:jvmTest :server:test :shared:testDebugUnitTest :shared:compileKotlinWasmJs
```

> **Never run `./gradlew build`.** It drags in the iOS release link tasks and takes ~48 minutes.
> There is no reason to run it — CI never does, and neither should you. Use the test command above,
> or a scoped task like `./gradlew :androidApp:assembleDebug` when you specifically need an APK.

## Architecture

This is a full-stack Kotlin project — one language, one codebase, four client targets + a server.

### core module

Targets: `android`, `iosX64/Arm64/SimulatorArm64`, `wasmJs`, `jvm`. Pure Kotlin (no Compose) so the server can depend on it without pulling UI code.

- `model/` — `@Serializable` data classes (`Account`, `FinancialEvent`, `CreditTerms`, `Subscription`, `RecurringRule`, and ~25 more). These are the wire types used by both the Ktor server responses and the client deserialization — do not add platform-specific code here. `Wallet`/`Transaction`/`TransactionType` in `Wallet.kt` are an early, largely superseded model kept for compatibility; `Account` + `FinancialEvent` are the ones actual features build on. **Bienes** (la casa, el carro) son un `Account` `INVESTMENT` con el campo `bien` (`Bien.kt`) — no un valor nuevo de `AccountType`, para no reventar APKs viejos — y **toda** cifra de «Tu plata» / condicionado / bienes / patrimonio neto sale de `patrimonioDe` (`Patrimonio.kt`), en cliente y server: no sumar el patrimonio a mano en ningún otro lado. Los **apartados** (plata separada dentro de una cuenta) también entran por ahí: `patrimonioDe(accounts, apartados)`.
- `repository/` — repository interfaces + Ktor-client impls. Constructed with an `HttpClient` and a `baseUrl` string; the caller provides the platform-specific engine.
- SQLDelight DB lives here. SQLDelight has no wasmJs artifact, so a `nonWasmMain` intermediate source set holds the DB/driver code and the generated SQLDelight Kotlin; `wasmJs` configurations exclude the `app.cash.sqldelight` group.

### shared module

The Compose Multiplatform UI library. Source sets:
- `commonMain` — all Compose UI screens and `App.kt` entry point. Uses `:core` for data types.
- `androidMain` — Android `actual`s (`Platform.android`, `BackHandler.android`, `FilePicker`, `SmsSensorSetupSection`) using `ktor-client-android` + `activity-compose`, plus the SMS-capture subsystem (`sms/` — bank filter, filter-config store, uploader, backfill — and `sensor/` — permission/hibernation/notification-access helpers) and its sibling, the bank-notification capture (`notificaciones/` — package allowlist, the pure capture decision, and the phone's small memory of what it already uploaded), both shared with the receivers/services/workers in `:androidApp`. (The Android *application* — `MainActivity` — lives in `:androidApp`.)
- `iosMain` — `MainViewController()` bridges to `ComposeUIViewController`; the iOS XCFramework (`baseName = "ComposeApp"`) is built from this module.
- `wasmJsMain` — wasm `actual`s + `ktor-client-js`. (The wasm executable `main()` lives in `:webApp`.)

Ktor HTTP engine is platform-specific: `ktor-client-android` for Android, `ktor-client-darwin` for iOS, `ktor-client-js` for wasmJs.

**Una lectura no se pide dos veces seguidas** (vuelta 78, `data/LecturasSinRepetir.kt`): `Repositories.paraLaApp` envuelve el repositorio en `InvalidaElInicioAlEscribir(LecturasSinRepetir(repo))`. Las lecturas de siempre (`getAccounts`, `getUserProfile`, los resúmenes, la historia `getEventsByDay`, `getUltimosDias`, créditos, tarjetas, pagos, ocurrencias…) **unen los pedidos iguales en vuelo** (single-flight) y devuelven lo que contestó bien hace menos de `FRESCURA_DE_UNA_LECTURA_MS` = 30 s (el mismo medio minuto del Inicio, `TTL_DEL_INICIO_MS`). **Cualquier escritura propia lo vuelve viejo** (sube `CacheDeLecturas.generacion`, que también sube al cerrar sesión), una falla no se recuerda (el «Reintentar» sale de verdad) y quien esperaba la misma lectura recibe la misma falla; si quien la pidió primero se cancela, la pide quien esperaba. **La bandeja «Por revisar» no pasa por ahí** (avisos, candidatos a pago de tarjeta, propuestas de la bandeja y de saldar): lo que llega en segundo plano tiene que verse al tocar su notificación. En el teléfono el repositorio de abajo es `LocalRepository`: sin conexión funciona igual. **Lo que cambia por fuera de la app no pasa por el envoltorio**, así que `olvidarLoFresco()` (`data/LoFresco.kt`) sube la otra mitad de la generación y marca vieja la carga del Inicio, sin borrar lo que se ve: lo llaman `TirarParaActualizar`, `BotonReintentar` (y con él `NoSePudoLeer`/`NoSePudoActualizar`), el aviso único, los «Reintentar» de los snackbars, el ↻ de Por revisar, la vuelta del segundo plano (`App.kt`; el Inicio a la vista vuelve a preguntar), y en el teléfono `SmsSyncWorker` tras subir, `confirmarDesdeLaNotificacion` tras anotar y el `SyncEngine` cuando sube algo (`alSubirAlgo`). Todo eso vive en el proceso de la app, así que comparten el contador; un proceso que no existía arranca sin nada fresco. Una lectura nueva que repita entre pantallas va en esa lista; `ElInicioNoRepitePeticionesTest` cuenta las peticiones con el cliente HTTP de verdad sobre un `MockEngine` (al abrir el Inicio `users/me` y `accounts` salen una vez; al volver antes de 30 s, ninguna).

**«Primer uso»: la guía por pasos de una cuenta nueva** (`ui/primeruso/`, `Screen.PrimerUso`, a pantalla completa y sin barra). **Sus pasos salen de la lista única de primeros pasos** (vuelta 54, `:core` `PrimerosPasos.kt`: `primerosPasos(LoQueYaHay, CapturaDelPrimerUso)` → período, cuentas, captura y pagos de cada mes, cada uno hecho o pendiente; sin captura posible en la plataforma, ese paso no va): Bienvenida + esos + Listo (`pasosDeLaGuia`), con barra de progreso, «Atrás», el botón principal (Empezar / Siguiente / Ir a Inicio; en el período y las cuentas se habilita solo cuando hay algo que guardar, en los pasos opcionales —captura y lo que pagas— siempre; vuelta 87), «Saltar este paso» en **todos** los pasos de en medio (también las cuentas) y «Ahora no». **Lo escrito no se pierde** (`BorradoresDeLaGuia.kt`): con un formulario escrito y completo el principal es «Guardar y seguir»; incompleto, el pie dice qué falta; saltar o «Ahora no» con algo escrito preguntan antes («¿Descartar el arriendo que escribiste?»). La misma lista pinta la fila «Te faltan N pasos ›» de Hoy (debajo de las acciones, `SduiRenderer(despuesDeLasAcciones = …)`; la × la oculta en `PropuestasDescartadasStore`), Tú → «Primeros pasos» (`ListaDePrimerosPasos`) y el resumen del final (`lineasDelResumen(lista, …)`); `Screen.PrimerUso(desde = paso)` abre la guía en un paso. Al abrir, la guía lee lo que ya hay (perfil, cuentas, tarjetas, reglas, movimientos). **«Lo que pagas cada mes» lleva también «Tu salario»** (vuelta 87: el mismo monto del paso del período; la regla de ingreso se crea al terminar). **No tiene escrituras propias**: el período guarda con `guardarElInicioDelMes` (la misma de Ajustes → «Inicio del mes», con «Es el día que me pagan» = `DIA_HABIL_ANTERIOR`), las cuentas con `crearCuentaConSaldo` (la de `CreateAccountSheet`: cuenta en $0 + apertura), las tarjetas con `createCard` y los pagos con `createRecurringRule`. La captura depende de la plataforma (`modoDeCapturaDe` → `capturaDelPrimerUsoEn`): en Android es la `SmsSensorSetupSection` de Captura del banco (hecha con el permiso o un aviso que ya llegó); en web/iOS, «Sube un extracto» —el archivo va a `PapelesCompartidos`, como «Subir comprobante»; hecho con cualquier movimiento— y, debajo y solo si el server tiene la dirección (`GET /api/correo-entrante/direccion`), el reenvío de correos con «Copiar» y el paso a paso de Gmail. **Quién la ve**: se abre sola tras `RegisterScreen`, y App.kt la pregunta una vez por sesión al llegar al Inicio (`revisarLaGuiaDePrimerUso`, para el registro HTML de la web y cuentas viejas): `debeAbrirseLaGuiaDePrimerUso` (`:core`) = `UserProfile.primerUsoEn == null` **y** ninguna cuenta de dinero (SAVINGS/CHECKING/CASH). Por eso no hubo migración: el dueño y toda cuenta con cuentas no la ven. Terminarla o «Ahora no» llama `POST /api/users/me/primer-uso`, que sella `users.primer_uso_en` (millis) solo la primera vez; el estado de la sesión (`GuiaDePrimerUso`, lo limpia `SessionManager.clear`) evita reabrirla si el server no contestó, y mientras está en curso la fila «Te faltan N pasos» del Inicio no se pinta. Lo saltado queda en «Primeros pasos». **Vuelta 88** (el Samsung del papá del dueño, navegación de tres botones y letra grande): la cáscara (`EsqueletoDeLaCascara`) descuenta la barra del sistema en toda pantalla sin barra de pestañas; `Boton` y `PildoraDeFiltro` tienen alto mínimo y el rótulo baja a dos renglones antes que cortarse; el pie usa `ParDeBotones` (apilados, el principal arriba, si no caben); los bancos bajan en renglones (se fue `enUnaFila`) y «Otro banco» busca en todos los de `bancosParaElegir` (`:core`); `SmsSensorSetupSection(conAccionPrincipal)` deja un solo amarillo por paso. Ver `docs/diseno/sistema.md` §85.

**El Inicio** (la pestaña se llama «Inicio» desde la ola R1 del rediseño; en el código sigue siendo `Screen.Dashboard`/`NavTab.HOY`) es el de la **opción 3** desde la vuelta 39 y se arma por SDUI desde `defaultDashboardDefinition()` (`:core`, **generación 10**) con las preferencias de «Editar inicio» aplicadas por el server (`inicioConPreferencias`). De arriba abajo: la **banda amarilla** (`SduiRenderer(conBanda = true)` + la barra del sistema en `App.kt`) con `EncabezadoDelInicio` (avatar con iniciales → Tú, «Hola, Juan» y el período, ocultar saldos y campana); el **héroe en tarjeta** (`HERO_BALANCE`: «Te quedan» con el enlace «Tu plata $X», la cifra que abre «¿De dónde sale?», «Para N días · $X por día» y la franja «Por confirmar» con «N por revisar»; la banda llega hasta media tarjeta y las acciones van siempre sobre el crema; **la cifra nunca arranca en $0**: `rememberCifraQueCambia` solo anima de una cifra real a otra); **8 acciones** (`ACCIONES`, `AccionDelInicio`: las seis de anotar hacen el atajo del «+» por `LocalAtajosDeAgregar`, más Revisar avisos y Preguntar a Movi); **«Próximo pago»** (`PROXIMO_PAGO`, `proximoPagoDelInicio` sobre `pagosEnElOrdenDePagos` —el orden de la lista de Pagos, `enOrdenDeFacturas`: vencido primero y después por fecha; vuelta 86—, con «Anotar pago»; si ya venció dice «Pago vencido · hace N días»); «Movi propone hoy» (`PROPUESTAS`: una `TarjetaDePropuesta` por tipo pendiente, tope 4, **sin el pago cuando la definición trae `PROXIMO_PAGO`**, lógica pura en `ui/dashboard/InicioDelRediseno.kt`; **los pagos, los débitos y lo que espera en «Por revisar» salen de UNA cola**, `colaDePendientes` en `:core` `ColaDePendientes.kt` —vencido primero y el monto más grande primero—, la misma que leen la campana y el resumen de Plan (el widget «Falta por pagar» y «Próximo pago» van por fecha, como la lista de Pagos); el número de «Por revisar» es `ConteoPorRevisar` en todos lados, con `DashboardSummary.movimientosPorConfirmar` del server); **«Últimos movimientos»** (`ULTIMOS_MOVIMIENTOS`: las 3 primeras filas de Actividad, `ultimosMovimientosDe` sobre `getUltimosDias(3)` —en la web `GET /api/events/by-day?ultimos=3`, solo los días de los últimos movimientos, enteros y sin anulados (`diasConLosUltimos`); Un APK de la generación 9 descarta los dos tipos nuevos y ve su Inicio de siempre. `DISPONIBLE_DEL_PERIODO` y `PATRIMONIO` son `SECCIONES_OPCIONALES` (`PreferenciasDelInicio.visibles`); ALERTS y BANNER quedan en la definición solo para APKs viejos. Las reglas de diseño (tokens, componentes `ui/components/ds/`, guardas) están en `docs/diseno/sistema.md` — obligatorias.

### androidApp module

`com.android.application` (NOT multiplatform). Holds `MainActivity`, the `AndroidManifest.xml`, `res/` (launcher icons, strings), and the two capture sensors — the SMS receivers/workers (`SmsRealtimeReceiver`, `SmsSyncWorker`, `SmsFilterRefreshWorker`) and the `NotificationListenerService` that reads bank-app notifications (`notificaciones/EscuchaDeNotificaciones`) — which reuse the `sms/` and `notificaciones/` logic that lives in `:shared`'s `androidMain`. Both sensors upload through the **same** `SmsSyncWorker` → `POST /api/sms/sync` → the «Por revisar» inbox (Movimientos; history in Ajustes → «Captura del banco»); they differ only in the worker's `origen` input, which decides which "last capture" mark gets written (mixing them would hide one sensor going mute). `applicationId = com.jvillada.movi`; module `namespace = com.jvillada.movi.app`. `MainActivity` is a **`FragmentActivity`** (not `ComponentActivity`): AndroidX `BiometricPrompt` — «Entrar con huella», see `:shared` `platform/HuellaDelAparato.android.kt` — mounts itself as a fragment and finds no host otherwise. That prompt is a **door, not a safe**: it gates opening the app, and the session token stays in ordinary app storage on purpose, so `SmsBackfillWorker`/`SmsSyncWorker` keep uploading bank SMS with nobody in front of the phone. An earlier version encrypted the token with a Keystore key that required a fingerprint and was removed whole for exactly that reason — don't reintroduce it without solving the background workers first (`data/EntrarConHuella.kt` carries the full rationale). It (Kotlin package `com.jvillada.movi`) calls `App()` from `:shared` and `DatabaseDriverFactory.init` from `:core` — the phone runs the full Movi app; the capture setup UI lives inside it (Ajustes → «Captura del banco» → «Captura en este teléfono» — permiso de SMS, acceso a notificaciones, hibernación e historial; `Screen.CapturaDelBanco`, called «Mensajes del banco» on web/iOS), not in a separate sensor screen. What's pending review (bank messages, events that came in on their own, card-payment candidates) lives in one inbox, `Screen.PorRevisar` (`ui/porrevisar/`), opened from Actividad (vuelta 40: con avisos del banco pendientes, la tarjeta «N avisos del banco por confirmar» con «Confirmar los N» —solo los que la fila de Por revisar confirmaría, por `loQueMoviEntendio` + `confirmarLoEntendido`/`confirmarElLote`, con `ConfirmarEnHoja` antes y sin deshacer— y «Revisar uno por uno»; sin avisos, el renglón «N por revisar») and the Hoy alerts. **Vuelta 44 · los avisos de un vistazo** (`docs/diseno/sistema.md` §48): cada tarjeta de la bandeja dice arriba «Categoría · Cuenta» (`LoQueMoviEntendio.linea`, entendido o no) y, si la fila confirmaría, «Confirmar» + «Cambiar» (Revisar aviso con `abrirCategoria`); «Confirmar los N» de la bandeja es la tarjeta y la hoja de Actividad (`ui/transactions/ConfirmarLosAvisos.kt`, compartida); confirmar dice «Anotado · …» sin deshacer; el código del remitente se nombra con `nombreDelOrigenDeCaptura` («85540» → «Bancolombia», también en el título de Revisar aviso); y la lista vuelve a sus filas por llave al volver de Revisar aviso (`ui/porrevisar/ElScrollQueSeConserva.kt`). **Vuelta 46** (§49): un aviso al que solo le falta la categoría (`LoQueMoviEntendio.faltaSoloLaCategoria`) la pide en su tarjeta —«Elegir categoría» abre las frecuentes y, elegida, `loQueMoviEntendio(categoriaElegida = …)` lo deja confirmable ahí y en el lote—; Revisar aviso no le pone ✓ a «Otros», a la cuenta por defecto ni al comercio sin leer; y elegir categoría es **un solo componente**, `ui/components/ds/FilaDeCategorias.kt` («Categoría … Todas ›» en un renglón y las pastillas), en Agregar, Revisar aviso, la tarjeta, «Repartir este gasto» (que ahora cambia también la fecha) y «Pagó otro». La franja «Por confirmar» del Inicio dice la suma de los avisos (`DashboardSummary.porConfirmarSuman` = `sumaDeLoPorConfirmar` en `:core`, entera o nada). Después de guardar, «¿se repite todos los meses?» solo sale si `seRepiteParaProponer` (`:core`) ve el mismo gasto ±15 % en 2+ períodos anteriores, y nunca tras repartir, un efectivo < $50.000 o un pago que saldó una ocurrencia (`RecurringOfferGate`).

**La captura por notificaciones no se cae callada** (vuelta 92; reglas puras en `:shared` `notificaciones/LaEscuchaSigueViva.kt` y `LoQueYaSubio.kt`). Android desenchufa el `NotificationListenerService` tras una actualización de la app, cuando mata el proceso o con el ahorro de batería, y no siempre lo vuelve a enchufar. (1) `onListenerDisconnected` anota la hora y pide `requestRebind`; `VigiaDeLaEscuchaWorker` (`:androidApp` `notificaciones/`, cada 6 h como el barrido de SMS, y una revisión al abrir que solo reconecta) aplica `queHaceLaVigia`: concedido y desconectado → `pedirQueReconecte`; si la lectura del acceso falla (`accesoANotificaciones` = `null`) es «no sé» y no hace nada; revocado tras haber funcionado → UNA notificación «Movi dejó de leer las notificaciones del banco · Activar» (canal «Captura del banco», «Activar» abre el ajuste del sistema; huella `revocado@<última conexión>`, se quita al reconectar). «Conectado» = `laEscuchaEstaConectada`: la marca de `onListenerConnected` sin desconexión posterior **y anotada por este mismo proceso** (un proceso que muere no alcanza a llamar `onListenerDisconnected`). (2) `onListenerConnected` barre `activeNotifications` por **el mismo camino** que `onNotificationPosted` (`procesarNotificaciones`: la decisión de siempre + la memoria), así lo que llegó con el listener caído entra sin duplicar; ignora lo publicado hace más de 48 h y lo que sube va silencioso (`SubidaDeNotificacion.silenciosa` → `CLAVE_SILENCIOSA` del `SmsSyncWorker`: sin «Movi anotó…» por cada una). (3) La memoria (`anotarSiEsNueva`) dedupe **por texto, no por llave**: la huella de siempre (texto + minuto) y, desde esta vuelta, la misma `StatusBarNotification.key` con el mismo texto dentro de 10 min (elegido: una reposición fuera de la ventana queda como fila de más, que se ve, en vez de perder en silencio el segundo cobro idéntico del día de un banco con id fijo) es una reposición; la misma llave con texto nuevo sí sube (bancos con id fijo), y otra llave con el mismo texto en otro minuto también (dos cobros). El resumen de grupo se ignora y `EXTRA_BIG_TEXT`/`EXTRA_TEXT_LINES` ganan, como antes. (4) Captura del banco → «Captura en este teléfono» dice `textoDelEstadoDeLaCaptura` («Conectada · última notificación del banco hace 2 horas» — la última de una app de la lista, subida o no — o «Desconectada · …» con «Reconectar», que pide el rebind y abre el ajuste). (5) Si la app no está exenta del ahorro de batería y hay captura, la sección ofrece «Quitar el ahorro de batería» (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, nunca se pide solo). (6) La lista de apps suma `com.todo1.davivienda.mobileapp` (server y respaldo); los demás bancos de la vuelta 88 no tienen paquete confirmado y no se adivinan. El camino de subida y el wire no cambiaron.

**El widget «Te quedan hoy»** (`widget/WidgetTeQuedan.kt`, `AppWidgetProvider` + `RemoteViews`, sin Glance) pinta la cifra del héroe de Hoy —«Te quedan», «Te pasaste por» o «Tu plata», la misma que decide `teQuedanDelInicio`— con «a las 9:40» debajo. **No pide red**: el texto lo arma `textoDelWidget` (`:shared` `ui/dashboard/TextoDelWidget.kt`, puro y probado) desde la instantánea del Inicio y su hora (`InstantaneaDelInicio.selladaEn`). Se repinta cuando la instantánea cambia (`InstantaneaDelInicio.alCambiar`, conectado en `aplicacion/MoviAplicacion.kt` —la `Application`, para que también el cierre de sesión de un Worker lo limpie—) y cada 30 min. - **Las alertas del banco por correo** (`correo/`, `routes/CorreoEntranteRoutes.kt`) son el **tercer hermano** de la captura de SMS y de la de notificaciones, y el único que vive en el server: cubren lo que el banco **se cobra solo** (cuota de manejo del cupo rotativo, su IVA, intereses, retenciones, débitos automáticos), que no llega por SMS ni publica notificación, y siguen funcionando con el teléfono apagado. Un proveedor de correo entrante (Postmark, Mailgun, Resend) postea el correo a `POST /api/correo-entrante`, **público** —no tiene sesión— y protegido por `INBOUND_EMAIL_SECRET`: sin esa env var la ruta contesta 503 y no acepta nada. El secreto viaja en `Authorization: Basic` (usuario cualquiera, contraseña = el secreto) o en `X-Movi-Correo-Secreto`, **nunca en la URL** — `CallLogging` imprime la ruta de cada petición. Un correo sin token resoluble contesta 202 y **no escribe nada**. `GET /api/correo-entrante/direccion` (autenticada) devuelve la dirección de reenvío de quien pregunta.

- **Confirmar un aviso arma las dos patas** (arreglo 1 de la auditoría de la ingesta, `routes/LasDosPatasDelAviso.kt`, `:core` `LasDosPatasDelAviso.kt`): el pago de una tarjeta propia, la cuota de un crédito propio, un traspaso entre cuentas suyas y el avance de una tarjeta se confirman con `DosPatasDelAviso` (operación, origen, destino, monto, fecha, nota y tres ids del cliente) y el server escribe las dos patas con **una sola función**, `escribirLasPatasDelAviso`, dentro de `confirmarElMismoPago` (bloqueo `FOR UPDATE` de los avisos, idempotencia, `evento_id` = la pata del dinero, `confirmado_en`). ## CI & deploy

- `.github/workflows/pruebas.yml` ("Pruebas") runs on every PR and push to master: the same four Gradle tasks from the Commands section above, plus a deploy guard that moves `local.properties` aside (Railway's image has no Android SDK, and Gradle's config phase would otherwise choke on it) before dry-running the wasm distribution task.
- **Railway auto-deploy is OFF (since 2026-09-13, to save money): merging to master does NOT deploy.** Deploy explicitly, in batches, with **`./scripts/desplegar.sh`** — don't hand-roll `railway up`. It uploads a folder without git — by default just a runtime `Dockerfile` that downloads the JAR built by GitHub Actions from a public GitHub release (next bullet), or with `--desde-fuente` an export of `origin/master` made with `git archive` (a `railway up` from a git worktree uploads the *main* checkout, not the worktree) —, always passes `--service movi-project` (the main folder was once linked to the **Postgres** service, and a bare `railway up` shipped Movi's Dockerfile to the database: «Build failed · Service: Postgres»), sets `MOVI_COMMIT_SHA` with `--skip-deploys`, waits for *its own* deployment id, and verifies the served web actually has the fonts. `/version` alone proves nothing: it reads a variable you set yourself. Production: `https://movi-project-production.up.railway.app`.
- **El JAR se arma en GitHub Actions, no en Railway (vuelta 69, 29-oct-2026).** Railway armaba todo con el `Dockerfile` de la raíz (wasm + fat JAR): 17 a 25 min contra un límite del plan de ~20 que no se puede subir, así que cerca de 1 de cada 2 builds moría con «DeadlineExceeded» y un despliegue pedía hasta 4 reintentos. Ahora `./scripts/desplegar.sh` usa el workflow **«Paquete para Railway»** (`.github/workflows/paquete.yml`, solo `workflow_dispatch` con entrada `commit`, más `push` a `paquete/**` para probarlo en una rama; **no** corre en cada push a master, cada corrida cuesta minutos): arma el wasm de producción, corre `el-paquete-web-trae-las-fuentes.sh`, mete la web en `server/src/main/resources/static/`, arma `:server:buildFatJar` y verifica que el JAR corra en Java 17 y traiga `static/index.html` y `figtree_regular.ttf`. Medido (29-oct): la corrida tarda 5,5 a 8 min (el wasm 4 a 6, el JAR ~1,3). **El fat JAR no lleva `sqlite-jdbc`** (`shadowJar` de `:server`, para que `--desde-fuente` arme el mismo): llega por el `jvm()` de `:core` (el espejo local de los clientes) pero el server no abre ninguna base SQLite, y eran 12,9 MB de nativos; con eso el JAR bajó de 100,6 a 87,1 MB (el resto son dependencias que sí se usan —bcprov, el SDK de Anthropic, POI—, la web son ~6 MB). **El server y el `jvm()` de `:core` se compilan para Java 17** (`jvmTarget` + `-Xjdk-release=17`): el runtime es `eclipse-temurin:17-jre`, y sin target explícito el JBR 21 de Actions emitía clases 65 que no cargan ahí; `paquete.yml` lo vigila.
- **Railway BAJA el JAR de un release público de GitHub (vuelta 84, 30-oct-2026).** En la vuelta 69 el script bajaba el artefacto de Actions y lo subía a Railway con `railway up`, pero subir 87 MB desde la Mac del dueño se cortaba («operation timed out») y cada despliegue caía al respaldo `--desde-fuente` (~20 min, al borde del límite). Ahora `paquete.yml`, después de verificar el JAR, publica el release **`paquete-<sha completo>`** (el mismo sha de `commit.txt` y del título de la corrida; `gh release create --prerelease --latest=false --target <sha>`, con `permissions: contents: write` solo en ese job; si ya existe, `gh release upload --clobber`) con `server-all.jar`, `server-all.jar.sha256` y `commit.txt`, y **ya no sube el artefacto `server-all`**. **El JAR es público** —el repo lo es— **por decisión del dueño** (30-oct): es código compilado y la web, sin secretos (los secretos son variables de Railway). **Limpieza:** la misma corrida deja los **5** `paquete-*` publicados más recientemente (por `publishedAt`: el `createdAt` de `gh release list` es la fecha del commit) y borra los demás con su tag (`gh release delete --cleanup-tag`); nunca toca un release ni un tag que no empiece por `paquete-`, y un borrado que falla no tumba la corrida. El script: (1) si el release del commit ya existe con sus tres archivos lo usa; si no, espera la corrida en curso o dispara una (una corrida exitosa cuyo release ya se limpió se arma de nuevo); (2) baja los tres archivos por la **URL pública sin autenticación** (`https://github.com/jvillad1/movi/releases/download/paquete-<sha>/…`, la misma que usa Railway) y exige `commit.txt` == el sha, la huella == `server-all.jar.sha256` y que el JAR traiga `static/index.html` y la fuente; (3) llena `scripts/despliegue-runtime/Dockerfile.plantilla` (`@@SHA@@`, `@@SHA256@@`; sale del mismo commit, o de origin/master si el commit es anterior) y sube con `railway up` una carpeta con **solo** ese `Dockerfile` y el `railway.toml` de runtime (~3 KB). La imagen (`eclipse-temurin:17-jre-alpine`, `MOVI_COMMIT_SHA`, `EXPOSE`, `CMD` de siempre) baja el JAR con `wget` (3 intentos) y `sha256sum -c`: **si la huella no coincide, el build falla**. Se eligió `wget` y no `ADD --checksum` (BuildKit también lo soportaría) para que el log del build distinga los dos fracasos: «MOVI-SIN-RELEASE» (no pudo bajar) contra «MOVI-HUELLA-DISTINTA». Link, `MOVI_COMMIT_SHA` con `--skip-deploys`, el id de ESTE despliegue, la espera y la verificación de `/version` + la cabecera TTF son los de siempre. **Respaldo automático, una vez, por `--desde-fuente`:** si `railway up` no devuelve id de despliegue, o si el build falla y su log (`railway logs <id> --build`) dice «MOVI-SIN-RELEASE» (la red de GitHub caída, o el release borrado en el medio). Cualquier otro build fallido —la huella distinta incluida— sigue siendo un error. Con `--sin-esperar` no hay respaldo por el build. **Respaldo a mano:** `./scripts/desplegar.sh --desde-fuente` hace exactamente lo de antes de la vuelta 69 (`git archive` + el `Dockerfile` completo de la raíz, que sigue como estaba) — para cuando Actions o los releases estén caídos; vuelve a chocar con el límite de ~20 min. **Ensayo:** `./scripts/desplegar.sh --ensayo [--commit <sha>]` hace todo menos `railway link/variable/up/logs` (consigue el release, lo baja y lo verifica, arma la carpeta, imprime el `Dockerfile` lleno y cuánto pesa, y la deja para mirarla); antes de que el workflow esté en master solo puede usar un release que armó un `push` a `paquete/**`.
- `.github/workflows/despliegue.yml` ("Despliegue") is manual only (`gh workflow run despliegue.yml -f commit=<sha>`): waits on `/version` via `scripts/esperar-despliegue.sh` (35 min timeout) and fails if the deployed commit never matches — Railway keeps serving the old build on a failed one.
- `scripts/` also has `build-apk.sh`, `generate-vapid-keys.sh` (web push), `seed-credits.sh` and
  `seed-subscriptions.sh`. Los dos `seed-*` comparten contrato: leen el token de `MOVI_TOKEN`
  (nunca por argumento — quedaría en el historial del shell), son dry-run salvo `--apply`, y son
  idempotentes contra lo que ya existe — con el alcance que eso tiene: la criba compara el
  nombre normalizado igual que el server más la moneda, así que atrapa un re-run pero **no** un
  registro que alguien haya escrito con otro nombre («Netflix» contra un «Netflix Colombia» que
  ya está). Para ese caso avisa y sigue; leé el dry-run antes de `--apply`.
  `seed-subscriptions.sh` resuelve la cuenta por NOMBRE contra `/api/accounts` al correr, en vez
  de guardar un id en el JSON, y en `--apply` cierra con un resumen y sale distinto de 0 si algún
  POST falló: un POST que falla no corta los que siguen.

## Key conventions

- **New REST endpoints** go in `server/src/main/kotlin/.../routes/` as extension functions on `Route`, then registered in `plugins/Routing.kt`.
- **New shared models** go in `core/src/commonMain/.../shared/model/` and must be annotated with `@Serializable`.
- **Platform-specific Ktor engine wiring** belongs in each `:shared` source set's dependency block, not in `commonMain`.
- The iOS Xcode project (`iosApp/iosApp.xcodeproj`) references the `ComposeApp` XCFramework at `shared/build/XCFrameworks/debug/ComposeApp.xcframework`. Always run `./gradlew :shared:assembleComposeAppDebugXCFramework` before building the iOS app — the Xcode build will fail if the framework is missing.
- **El desembolso de un crédito es plata que ENTRÓ** (decisión del dueño): las dos patas de un par
  que sale de una cuenta LOAN llevan `DESEMBOLSO_CATEGORY` («Desembolso de crédito»), la del dinero
  suma en «Entró»/«Ingresos» y la del crédito no (la excluye el tipo de cuenta). No es reservada
  —cuenta como cualquier categoría— pero solo la escribe `transferLegsFor`: `POST /api/events` la
  rechaza suelta, renombrar/unificar la protegen (igual que a `CUOTA_CATEGORY`), y Movi AI dice cuánto
  de los ingresos es deuda. El abono extraordinario sigue siendo un traspaso puro.
- **El período arranca el día que pagan** (`:core` `PeriodoFinanciero.kt`): el corte (`users.period_cutoff_day`) se corre si cae sábado, domingo o festivo de Colombia (`FestivosDeColombia.kt`, calculados: Ley Emiliani + Semana Santa) según `users.period_weekend_rule` (`SiElCorteCaeEnFinDeSemana`: `ESE_DIA` por defecto, `DIA_HABIL_ANTERIOR` —el del dueño: el 25 domingo → viernes 23, el 25-dic → 24—, `DIA_HABIL_SIGUIENTE`; se elige en Ajustes → «Inicio del mes»), y las excepciones a mano de `users.period_starts` **ganan** sobre esa regla. Todo sale de `inicioDelPeriodo`; armar los ajustes desde un perfil es `UserProfile.ajustesDelPeriodo()` (server: `ajustesDePeriodoDe`), nunca `PeriodSettings(corte, inicios)` a mano. El ingreso recurrente del día de corte (el salario) se **espera** el día que arranca su período (`fechaEsperadaDelIngreso` / `fechaEsperada`): eso se muestra en «Próximos» y el checklist, pero el sello sigue siendo el mes del día de la regla.
- **Un 401 de Movi cierra la sesión, al primero** (26-oct-2026, tras rotar `JWT_SECRET`: Android
  pintaba el caché con el token muerto y la captura del banco fallaba callada). La regla vive en
  `laSesionTras` (`:shared` `data/LaSesionRechazada.kt`): solo un 401 del host de Movi, fuera de
  `/api/auth/`, de un pedido que llevaba **el token guardado**; sin red, un 5xx o un 403 la sesión
  sigue (Movi funciona sin conexión con lo guardado). Ya no hay racha de «tres 401»: el server da
  401 solo cuando el token no pasa. `SessionManager.seRechazoElToken` cierra como el logout y anota
  `sesionRechazadaDe`, que el login dice («Tu sesión se cerró…», también el overlay de la web).
  En Android, `MoviAplicacion` engancha `alRechazarseLaSesion` (UNA notificación «Movi dejó de
  recibir los mensajes del banco» si la app no está a la vista) y `alEntrar` (la quita, sube
  `CapturasPorSubir` con `SubirCapturasPorSubirWorker` y barre el inbox). `SmsSyncWorker` con un
  401 o sin sesión rechazada-por-el-server **guarda** la captura en vez de descartarla (las
  notificaciones del banco no se pueden volver a leer); lo de otra persona nunca se le sube a la
  que entra.
- **Las pruebas Robolectric arrancan con los `object` de la app en cero.** Todas las clases de
  `:shared:testDebugUnitTest` comparten un fork de JVM y un sandbox, así que el estado estático se
  filtraba de una clase a la siguiente (y ya hizo intermitente a una prueba que medía una pantalla).
  Lo resuelve `shared/src/androidUnitTest/kotlin/com/jvillada/movi/AppDePrueba.kt`, declarado en
  `androidUnitTest/resources/robolectric.properties`: limpia antes de **cada** método, sin que
  ninguna clase tenga que hacer nada. Si agregas un `object` mutable que una pantalla llene, fíjate
  que `SessionManager.clear()` lo limpie y agrégalo a `ElForkLlegaLimpioTest`.
- **El movimiento pasa por un solo lugar** (Ola 1 · «Que Movi se sienta viva», `:shared` `theme/Movimiento.kt`): duraciones (180/220/280 ms), curvas (entrar = emphasized decelerate) y specs; con el sistema pidiendo menos movimiento (`LocalMovimientoReducido`, expect `movimientoReducidoDelSistema`) todo pasa en el acto. App.kt anima la **pila entera** con `AnimatedContent` (clave = la pantalla de arriba, la misma del `SaveableStateProvider`) y `direccionDe(antes, despues)` decide apilar/volver/fundido. **Una raíz de pestaña reemplaza la pila** (`NavStack.pilaDeLaPestana`: `[Hoy]` o `[Hoy, raíz]`; las raíces son Inicio, Actividad, Pagos y Tú), y re-tocar la pestaña activa sube al principio (`SubirAlRetocarLaPestana` junto al `ScrollDesdeLosMargenes` de cada raíz).
